When you call `paymentForm.init(...)`, Flex accepts three callback functions. The main payment result reaches your frontend through `responseCallback(response)`.

<Info>
  Use `responseCallback(response)` as the main entry point for frontend results. The returned JSON follows the **E-commerce authorization API** structure for the payment method selected in Flex.
</Info>

## Callbacks available

<CardGroup cols={3}>
  <Card title="responseCallback" icon="circle-check">
    Runs when the flow reaches a business outcome and returns the JSON response.
  </Card>

  <Card title="trackingCallback" icon="chart-line">
    Runs for flow events such as method changes, clicks or progress through the form.
  </Card>

  <Card title="onErrorCallback" icon="circle-xmark">
    Runs when a technical error occurs while loading or running the component.
  </Card>
</CardGroup>

## Example of implementation

```javascript theme={"system"}
function responseCallback(response) {
    console.log("-------Response-------");
    console.log({response});
}

function trackingCallback(trackdata) {
    console.log("-------Event tracking-------");
    console.log({trackdata});
}

function onErrorCallback(error) {
    console.log("-------Processing error-------");
    console.log({error});
}

paymentForm.init(
    document.querySelector("#demo"),
    responseCallback,
    trackingCallback,
    onErrorCallback
);
```

## How to interpret responseCallback

<Note>
  The field `response.payment_method` indicates what reference to PayIn you have to use to interpret the JSON response returned by Flex.
</Note>

<Warning>
  Do not use `response.meta.status.code` to decide whether a payment was approved or declined. It only describes service processing. Read `response.transaction.state` and confirm the result from your backend using a [query](/en/api-reference/payin/get-ecommerce-transaction) or server notifications for the payment method.
</Warning>

<Tabs>
  <Tab title="CARD">
    The `response` object follows the contract of [Card authorization API](https://docs.pay-me.com/payin/autorizacion-tarjeta).

    If your flow uses Redirect or 3DS authentication outside the same screen, complete this reading with [Considerations for Redirect methods](https://docs.pay-me.com/payin/autorizacion-metodos-con-redirect).
  </Tab>

  <Tab title="YAPE">
    The `response` object follows the contract of [Yape authorization API](https://docs.pay-me.com/payin/autorizacion-yape).

    Even when the result arrives through `responseCallback`, validate consistency from the backend before confirming the order.
  </Tab>

  <Tab title="BANK_TRANSFER">
    The `response` object follows the contract of [Bank transfer authorization API](https://docs.pay-me.com/payin/autorizacion-transferencia-bancaria).

    This method may require later confirmation. Do not use the frontend as the only source of truth; use [Consultation](https://docs.pay-me.com/payin/consulta-transferencia-bancaria) or [Notifications](https://docs.pay-me.com/payin/notificaciones).
  </Tab>

  <Tab title="QR">
    The `response` object follows the contract of [QR authorization API](https://docs.pay-me.com/payin/autorizacion-qr).

    Generating a QR or displaying an initial response does not confirm final payment. Use [Consultation](https://docs.pay-me.com/payin/consulta-qr) or [Notifications](https://docs.pay-me.com/payin/notificaciones) to complete your business logic.
  </Tab>

  <Tab title="CUOTEALO">
    The `response` object follows the contract of [Cuotéalo authorization API](https://docs.pay-me.com/payin/autorizacion-cuotealo).

    Confirm the final state after redirection or follow-up using [Consultation](https://docs.pay-me.com/payin/consulta-cuotealo) or [Notifications](https://docs.pay-me.com/payin/notificaciones).
  </Tab>

  <Tab title="PAGOEFECTIVO">
    The `response` object follows the contract of [PagoEfectivo authorization API](https://docs.pay-me.com/payin/autorizacion-pagoefectivo).

    Generating a CIP or payment link does not mean funds have been received. Confirm the result using [Consultation](https://docs.pay-me.com/payin/consulta-pagoefectivo) or [Notifications](https://docs.pay-me.com/payin/notificaciones).
  </Tab>
</Tabs>

<Warning>
  Use `trackingCallback` for events and `onErrorCallback` for technical failures. Neither replaces the business logic built around `responseCallback` and backend confirmation.
</Warning>

## Life cycle of the instance

<Note>
  The following examples use `unmountFlex()` from the [responsive example](/en/virtual-payments/checkout-web/customize-checkout#responsive-conduct). Adapt cleanup to your presentation: embedded, popup or expanded.
</Note>

`paymentForm.terminate?.()` ends Flex's internal processes, listeners and resources. This is different from removing the form from the DOM (`flexContainer.innerHTML = ""`) and applies to every presentation type.

<Info>
  The `?.` operator calls `terminate()` only if the method exists. This avoids errors if the loaded Flex version does not implement it.
</Info>

### When to unmount each presentation

| Presentation  | When to Unmount                                                          | Following visual action                                       |
| :------------ | :------------------------------------------------------------------------ | :------------------------------------------------------------ |
| Embedded   | When hiding checkout, changing sections or navigating to another screen. | Remove or replace the container that held Flex.            |
| Popup (modal) | When the customer closes the popup or the flow ends.                   | Hide the overlay and return the focus to the main interface. |
| Expand     | When collapsing checkout or leaving an expanded view.               | Collapse the panel or restore the previous layout.               |

In all 3 cases, first process any outstanding result and then run `unmountFlex()` before updating the visual presentation.

<Warning>
  Do not modify the internal styles of Flex. Call `unmountFlex()` When you withdraw the form, regardless of whether it's embedded, into a popup or an expanded view.
</Warning>

### Your own result screen

With `settings.display_result_screen: false`, Flex does not display its final screen. Your application must receive the `response`, evaluate the transaction state and display its own result screen.

<Steps>
  <Step title="Mount form">
    `paymentForm.init(...)` mounts Flex inside the container.
  </Step>

  <Step title="Receives result">
    Flex runs `responseCallback(response)`. Read `response.transaction.state` and perform the relevant business validations.
  </Step>

  <Step title="Show your screen">
    Save `response` in your application state, then navigate to or render your result screen.
  </Step>

  <Step title="Unmount Flex">
    After processing the result, call `terminate()`, clear the container and update the embedded, popup or expanded presentation.
  </Step>
</Steps>

```javascript theme={"system"}
const paymentForm = new FlexPaymentForms({
  nonce,
  payload,
  settings: {
    display_result_screen: false
  }
});

const flexContainer = document.querySelector("#flex-container");

paymentForm.init(
  flexContainer,
  (response) => {
    const transactionState = response.transaction?.state;

    // Process and retain the response before unmounting Flex.
    showMerchantResultScreen({ transactionState, response });
    unmountFlex();
  },
  (tracking) => {
    console.log("Tracking event", tracking);
  },
  (error) => {
    console.error("Flex error", error);
  }
);
```

<Warning>
  Do not call `terminate()` before receiving and processing `responseCallback(response)`. Ending the instance early can interrupt the flow and lose the result Flex was about to return.
</Warning>

### Reusable cleanup

Encapsulate initialization and cleanup in a framework-independent controller. Use it in plain JavaScript or connect it to the lifecycle of React, Vue, Angular or another framework.

```javascript theme={"system"}
function createFlexController({
  container,
  configuration,
  onResult,
  onTracking,
  onError
}) {
  let instance = null;

  function mount() {
    // Avoid retaining a previous instance when reopening Flex.
    destroy();

    instance = new FlexPaymentForms(configuration);
    instance.init(container, onResult, onTracking, onError);
  }

  function destroy() {
    instance?.terminate?.();
    instance = null;
    container.replaceChildren();
  }

  return { mount, destroy };
}

const flexController = createFlexController({
  container: document.querySelector("#flex-container"),
  configuration: {
    nonce,
    payload,
    settings: {
      display_result_screen: false
    }
  },
  onResult: responseCallback,
  onTracking: trackingCallback,
  onError: onErrorCallback
});

// Open or recreate the form.
flexController.mount();

// Destroy the instance when closing, navigating away or removing the view.
// flexController.destroy();
```

<CardGroup cols={3}>
  <Card title="JavaScript" icon="code">
    Call `destroy()` before withdrawing the container from the page.
  </Card>

  <Card title="SPA integration" icon="arrows-rotate">
    Call `destroy()` on route changes or when unmounting the view.
  </Card>

  <Card title="Dynamic presentation" icon="window-restore">
    Call it when hiding the embedded block, closing the popup or collapsing an expanded view.
  </Card>
</CardGroup>

`container.replaceChildren()` clears the container, like `container.innerHTML = ""`, without depending on a framework.

<Note>
  `terminate()` does not return the payment response. The result arrives through the first callback passed to `paymentForm.init(...)`. See [Capture callback functions](/en/virtual-payments/checkout-web/results-and-cleanup) to interpret and confirm the operation.
</Note>

### Management of closure with show\_close_button

Set `settings.show_close_button: true` to display the native Flex close button. This works with embedded, popup and expanded presentations.

```javascript theme={"system"}
const paymentForm = new FlexPaymentForms({
  nonce,
  payload,
  settings: {
    show_close_button: true
  }
});
```

When the customer presses the button, Flex sends `cerro el carrito` through `onErrorCallback`. Although it uses the error callback, this message represents a voluntary customer action, not a technical failure. Keep this literal message unchanged in code.

<CardGroup cols={3}>
  <Card title="Show the button" icon="circle-xmark">
    Enable `show_close_button` in `settings`.
  </Card>

  <Card title="Handle the event" icon="code-branch">
    Identify the exact message `cerro el carrito` in `onErrorCallback`.
  </Card>

  <Card title="Close presentation" icon="power-off">
    Call `onClose()` to unmount Flex and update the interface.
  </Card>
</CardGroup>

Implement a separate branch for voluntary closure and handle other messages as technical errors:

```javascript theme={"system"}
function getFlexErrorMessage(error) {
  if (typeof error === "string") return error;
  return error?.message ?? "";
}

function onErrorCallback(error) {
  const errorMessage = getFlexErrorMessage(error).trim();

  if (errorMessage === "cerro el carrito") {
    onClose();
    return;
  }

  // Handle other messages as technical errors.
  handleFlexError(error);
}

function onClose() {
  unmountFlex();

  // Hide the popup, remove the embedded block or collapse the expanded view.
  hideFlexPresentation();
}
```

The closing flow is `show_close_button` → `onErrorCallback` → `onClose()` → `unmountFlex()`. `hideFlexPresentation()` represents the visual logic of your application: remove the embedded block, hide the popup or collapse an expanded view.

<Warning>
  Call `onClose()` only after matching the exact message `cerro el carrito`. Continue handling any other value received by `onErrorCallback` as a technical error.
</Warning>
